AUTHORIZED WEB TESTING — PATCHRIOT PILOT

1. Establish scope and baseline. Fetch the approved homepage, identify redirects without following them outside scope, and inspect the actual content type, headers, resource paths and framework. Collect only the pages needed for the objective.
2. Map the exposed application. Read linked JavaScript and API references on approved origins. Distinguish application routes from SPA fallback pages: a 200 response that repeats the homepage is not a leaked file. Compare hashes, content types and meaningful body text.
3. Form hypotheses before testing. Examples: a sensitive unauthenticated endpoint; reflected input reaching an executable context; an overly permissive CORS response; unsafe cache behavior; an exposed source map with genuinely sensitive content; a redirect that accepts a foreign destination. Use a harmless unique marker and control request. Do not assume a response is vulnerable just because a scanner would flag it.
4. Reproduce within the approved methods. Do not buy, trade, withdraw, change real accounts, create persistent exploit payloads, enumerate real customer records or stress the service. An active scope (web_active_v1 or web_active_v2) permits bounded POST changes to disposable test data only. Use only the supplied test account through the relay; never follow discovered credentials. Without those explicit scope options, report the need for a separately approved test.
5. Verify claims. For CORS, compare trusted, arbitrary and null Origin cases and credentials behavior; public content with a wildcard is not automatically a vulnerability. For reflected input, distinguish encoded text from executable HTML/JS; without browser execution, state that limitation. For exposed files, distinguish intended public configuration from secrets. For redirects, record the exact Location and code. For throttling and lockout, retain attempt counts, timing, identity scope and responses. A short burst leaves higher thresholds untested. Report a bypass only with evidence of an enforced boundary and an approved bounded comparison against that same boundary.
6. Keep evidence useful. Record request IDs, request method/URL/headers, actual status, relevant excerpts and negative controls. The broker captures bounded evidence; do not claim full-content coverage when truncated. Never put secrets or private customer data into a public report.
7. Challenge severity. State the prerequisite, actual impact and smallest useful fix. Keep confirmed observations separate from hypotheses about the implementation or wider access. A few tested paths do not establish server-wide behavior or full database access. Mark HTML reflection as observed when script execution was not tested; do not label an XSS candidate as a reproduced XSS exploit. The next role should be able to repeat the test from your reproduction text.
8. Keep the report checkable. Every finding needs relevant request IDs from this role. If an earlier claim could not be checked, describe that gap in limitations; do not create a finding with empty or unrelated citations. Read original JSON files in small selected pieces when terminal output is shortened.
9. Stop unproductive guessing. Start with actual links, forms and scripts, then test representative boundary cases and negative controls. Repeating the same rejection across a long list of record IDs or invented parameter names does not prove safety. Report the tested bounds and reserve time for the useful findings and report.
10. Make the fix usable. When the observed stack is known, include a short illustrative code example in suggested_action, using a fenced code block inside the JSON string. Otherwise describe the required behavior without inventing a language or framework. State the regression check and its correct expected result: rejecting a malformed ID with 400 is different from returning a valid product. These are untested recommendations, not patches applied to the customer's source. Keep the summary to a few sentences; put probe details in the relevant finding and recorded requests.

Checked OWASP WSTG v4.2 identifiers (https://wstg.owasp.org/v4.2/):
- WSTG-INPV-01: reflected cross-site scripting; unencoded reflection alone does not prove execution.
- WSTG-INPV-05: SQL injection.
- WSTG-CLNT-07: cross-origin resource sharing.
- WSTG-CONF-07: HTTP Strict Transport Security, not every missing security header.
Use these stable identifiers when applicable. Omit an unverified identifier rather than inventing chapter numbers or copying a prior role's classification. This reference does not limit the permitted test topics.

Additional scanner leads are in /work/tool-results.json. Inspect the referenced upstream evidence, scanner limitations and account context. A missing header, schema publication or reflected string alone does not demonstrate an exploit. Reproduce the minimum security impact, include a negative control, and retain rejected or unresolved hypotheses in the assessment explanation. The coverage ledger distinguishes recorded requests from unresolved vulnerability classes. Its deferred entries do not erase verified candidate-specific findings.
